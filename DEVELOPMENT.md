# Правила разработки Well Importer

## Ветки

- `main` — стабильная рабочая версия.
- `feature/<name>` — крупная новая функция.
- `fix/<name>` — исправление ошибки.
- `refactor/<name>` — переработка внутренней архитектуры без изменения поведения.

## Коммиты

Рекомендуемые префиксы:

- `feat:` — новая функция;
- `fix:` — исправление ошибки;
- `refactor:` — рефакторинг;
- `docs:` — документация;
- `chore:` — техническое обслуживание.

Пример:

`fix: корректно переносить номер скважины в площадной круг`

## Комментарии в коде

Комментарии должны объяснять:

- назначение класса или метода;
- неочевидную бизнес-логику;
- особенности API QGIS/PyQGIS;
- причины преобразования CRS;
- правила транзакций и сохранения слоя;
- причины защитных проверок и fallback-логики.

Не нужно комментировать очевидные присваивания, циклы и стандартные вызовы API.

## Каждое обновление

Для каждого значимого обновления:

1. Сделать отдельный коммит с понятным сообщением.
2. Для крупной функции или рискованного исправления использовать отдельную ветку и Pull Request.
3. В описании PR указать: что изменено, зачем, какие риски, как проверено.
4. Если изменение крупное или исправляет критическую ошибку — обновить `CHANGELOG.md`.
5. Перед слиянием проверить синтаксис Python и структуру ZIP-плагина.

## Версии

Номер версии меняется только при согласованном релизе. Внутренние правки одной версии могут публиковаться отдельными коммитами без изменения `metadata.txt`.
